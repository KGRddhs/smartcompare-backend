Follow-up of #205 (W0-4e2, the chunked yielding scan in `structured_comparison_service._lazy_bh_pdp_backfill`, `ENABLE_PRICE_PARSE_OFFLOAD` ON only).

**What differs from `re.findall`.** The flag-ON scan runs the base href pattern over `html[start : min(start + CHUNK + OVERLAP, n)]` for `start in range(0, n, CHUNK)` and keeps a match only when it starts before `start + CHUNK`. When a slice boundary falls INSIDE a match whose URL text ends in the literal `href=` just before its closing quote (two consecutive URL values chained), the next slice restarts inside that match and collects one extra overlapping match. Pure-re measurement (pr text of #205): with chained URLs the R11 algorithm differs from `findall` on 1,533 of 3,000 synthetic pages, a resume guard on 885, a continuation form on 0; without chains all three agree on every page. Real retailer search pages were never observed to chain `href=` inside a URL value; flag OFF is the base `findall` and is unaffected.

**Candidate fix (W0-4e3).** The continuation form: carry the last kept match's end across the slice boundary and start the next slice's `finditer` at `max(start, last_end)`, so a match cannot be re-entered. It must keep the R14 slice-bound pin (`len(slice) <= CHUNK + OVERLAP`), the R15 overlap pin (a ~4 KB href spanning a boundary) and the E2a identity rows green, and add an identity row over the chained fixture (`aaa-href=` / `bbb-href=` / `ccc/`). Same flag, corpus harness blind (it never enters the backfill), so the gate is the E2 identity matrix plus the CI-order set.

**Severity.** Low: one extra candidate href on a pathological page, filtered afterwards by `validate_scrape_url` / `score_source`; no user-visible change measured.
