- R-MON1-16 (review B1, ADOPTED) THE OPENAI OUT-OF-CREDIT RULE: `quota` = an openai APIStatusError with status 429 AND (its structured `code` is one of credit_balance_exhausted, insufficient_quota, organization_spend_limit_exceeded, project_spend_limit_exceeded, organization_usage_limit_exceeded OR its structured `type` is insufficient_quota), read through getattr only, never from message text. - R-MON1-17 (review B2, ADOPTED) A PROBE SUCCESS PROVES AUTHENTICATION ONLY. It may move `rejected` to `ok` only when that rejection was probe-sourced or carried status 401. It never clears `quota`, never clears a dispatch-sourced 403, and fires no recovery event while a dispatch-sourced quota or 403 state is held. Rows P13 and P14 of the review, with a killing mutant.
- R-MON1-18 (review B3, RULED: stricter than both options) A PROBE-SOURCED REJECTION NEEDS THE STRUCTURED INVALID-CREDENTIAL SIGNAL: openai = status 401 AND structured code invalid_api_key; anthropic = status 401 AND structured type authentication_error. Every other probe failure (a 401 or 403 without that signal, e.g. a restricted credential without permission for the metadata endpoint; a timeout; a 5xx; a rate limit) is INCONCLUSIVE: the state does not change, and one INFO line per process per (provider, exception class) records it. A DISPATCH 401 or 403 is always `rejected` (the real call failed). So a restricted credential can neither false-alarm nor flap. In addition the O3 window's owner step checks it (PP4): after the flip, `/health` must show the probe-sourced state within the first tick while a comparison succeeds; an `unknown` that persists with the probe ON is the signal to roll the flag back or to fix the credential's permissions.

A process lives from deploy to deploy, so a once-per-process latch would mute a second outage.
