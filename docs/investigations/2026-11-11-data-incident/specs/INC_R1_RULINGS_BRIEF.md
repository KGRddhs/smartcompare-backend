R1-3 MODULE. A new app/services/product_resolver.py with one async entry that takes the two typed names (already sanitized) plus the request's routing context and returns, per side: brand, line, concentration (a lexicon concentration or None), size_ml (only when typed), confidence (high / medium / low), source (lexicon / llm / none), candidates (0 to 4, each brand + line + concentration), is_fragrance (True / False / None). It runs once per comparison, before _resolve_pair_category, and never raises into the orchestrator (any exception = the side unresolved with source none, logged).

R1-4 DETERMINISTIC ARM (always when the flag is ON; no network). R1-5 CLAUDE ARM. When the deterministic arm leaves a side without house and line, ONE call for the pair on a NEW router site "resolve" (role text; a SiteSpec with a closed JSON schema in the form of DISAMBIGUATE_SCHEMA; a small claude_max_tokens about 384), dispatched exactly the way the "disambiguate" site is (openai_service.py:905 and llm_router.route), so the consent routing, the OpenAI egress stop, the spend breaker and the ledger apply unchanged; bounded by PRODUCT_RESOLVER_TIMEOUT_SECONDS. The prompt gives both typed names (as data, fenced as user input) and the deterministic hints; rules: identify the perfume; never invent a product; a brand-less name gets a house only when the line name is distinctive; a 1-2 letter misspelling of a known line resolves to that line; a base line typed without a flanker word resolves to the base product with the flankers listed as candidates; a name that is not a fragrance gets is_fragrance false. At most one Claude call per comparison; a per-process LRU (normalized pair key, TTL 24 h, at most 2,000 entries) avoids repeats; no Redis read on this path (Redis reads time out in production today).

R1-6 ACCEPTANCE GUARD (deterministic; the model is never trusted alone). A Claude answer for a side is accepted only when ALL hold: (a) is_fragrance is true; (b) confidence is high; (c) the brand folds to a house of the R1-4 union list, OR every token of the brand appears in the typed text (the user named a house we do not list); (d) for Latin-script input, the typed text minus the house words is within the R1-4 edit-distance rule of the returned line (token-wise); for Arabic-script input (d) is waived and (c) must hold through the list (stated limit). Otherwise the side is UNRESOLVED; the model's candidates that pass (a) and (c) ride along.

R1-7 DECISION. (i) Both sides resolved: rewrite each product dict: brand = the resolved house display name, name = the resolved line (with the flanker), variant = the concentration (and a typed size), search_query = "<brand> <line> <concentration>" (the concentration only when known), category = the fragrance category value the pair resolver uses. Every search, price gate, cache key and later KB lookup then inherits the canonical identity. (ii) A side unresolved in a fragrance-intended pair (the other side resolved as a fragrance, or the Fragrances chip was sent, or the Claude answer marked that side is_fragrance with low or medium confidence, or marked it not a fragrance while the other side is one) and PRODUCT_RESOLVER_ASK on: refuse BEFORE any fetch with the existing coded refusal both live bundles render as the "add the brand and the fragrance name" message (the spec measures the exact code and reason pair, believed INSUFFICIENT_DATA with reason placeholder_identity, errorCopy.ts:83-93, error_handler.py:84, on the sync and the stream routes), with an additive candidates list for the future picker; no credit consumed, no lifetime count, no history row (R-A3: the spec measures the refund path for a Step-1 refusal).
