## 1. The answer in plain words

1. **It ran on Claude, not OpenAI** (the relay's /health reading; the code agrees: a consent-3 account routes text to Anthropic, llm_router.py:343-355). The text model is claude-haiku-5-5 by default (model_config.py:218, 227-234).
2. **The model is not what failed. The app never worked out which perfumes the owner meant.** The app sends the two typed fields as they are. The server then sets the brand to empty and searches the typed words exactly as typed (structured_comparison_service.py:4438-4453, the same at 5140-5153 and 1959-1971). Nothing afterwards resolves the name: no brand detection, no spelling correction, no catalog lookup, no "did you mean" (ESTABLISHED, confirmed by the reviewer).
3. So "Tyger" was searched as a bare word: Google Shopping returned truck parts and Google Images returned a page of William Blake's poem, which the picture step accepted with no check at all (image_service.py:57-67, 295-311). "stronger with you" was searched with no brand, so the price checks that need a brand name (decant floor, wrong-brand fence) never switched on, and a noon.com listing of unknown size and flanker won (price_service.py:1626-1632, 7164-7166; noon_service.py:215-243).
4. Claude was then asked to write specs and reviews from search results about truck parts and a poem. It answered honestly that it had no data. **Our server turned that "no data" into a page that looks complete**: eleven "N/A" spec fields became eleven rows of dashes; the same eleven empty fields were counted as eleven "citations", which made the Specs chip read **High**; they also produced the Versatility bar and the line "stronger with you leads on Versatility"; and Claude's own sentence "No review data was available..." was shown as the review text.
5. A newer or bigger model (Sonnet) would not fix this: it would be asked about the wrong product with the wrong search results. The fix is to **resolve the product first, or ask the user**, and to **never present empty data as a confident result**. Claude does help with the first part: it knows that "Tygar" is a Bvlgari line and that "Stronger With You" is Emporio Armani.

## 4. Research: how to do this well (sources and licences in R1 / R2; the reviewer re-opened them)

**Resolving a typed name (R1).** Every large shop and price-comparison system uses the same pattern: (1) find candidates in your OWN catalog with cheap matching (trigram, edit distance, phonetic codes, an alias table); (2) let a model, or rules, choose ONLY among those candidates, with "none of these" as a real answer; (3) two thresholds: above the high one resolve silently, in the middle ask "which one did you mean?" with at most about four choices, below the low one say so; (4) only then search for offers, with the canonical name. Sources: Instacart's Intent Engine, Shopify catalog clustering, idealo, Bing Shopping, Etsy spelling correction, entity-linking papers (arXiv 2601.05192, 2601.08500, NAACL 2024 GenDecider). A worked example: "Tyger" vs "Tygar" is one edit apart; this only works because the candidate set is limited to perfumes, never the open web.

**Reusable code (licences read from GitHub):** RapidFuzz (MIT), jellyfish (MIT), SymSpell / symspellpy (MIT), anyascii (ISC), pgvector (PostgreSQL licence), sentence-transformers (Apache-2.0), Splink and dedupe (MIT, offline offer merging only). AVOID: Robotoff, Zingg, openfoodfacts-server (AGPL-3.0: idea only, never copied into our public repository).

**Open datasets.** No free perfume catalog exists that we may take. Wikidata (CC0) has about 402 perfume items, no barcodes, and neither Tygar nor Stronger With You. Open Beauty Facts (database ODbL, share-alike; images CC BY-SA) has a few Stronger With You barcodes, no Tygar; keep anything taken from it in a separate table. GS1 barcode data only under a signed agreement (the owner's step). **FORBIDDEN whatever licence they state:** FragDB (a full crawl of a perfume community site) and the Kaggle/TidyTuesday Parfumo set (scraped from Parfumo). We must build our own catalog from brand sites and the Gulf shops we already read, with Claude normalising offline.

**Lawful Gulf sources (R2).** Product-page structured data (schema.org JSON-LD), the WooCommerce Store API (documented as public) and Shopify's documented product endpoint are the clean sources, per host, under robots.txt (RFC 9309) and the owner's terms verdict. Note: Shopify does not document the `/products.json` endpoint our feed walker uses; the owner's terms verdict should cover it explicitly. Salla and Zid catalogues need each merchant's opt-in (a partnership track). Affiliate feeds: Admitad has per-advertiser product feeds; ArabClicks publishes no feed documentation (ask them). Amazon.ae / .sa (Creators API): a sales threshold is reported by third parties, not on Amazon's own pages (LIKELY). noon has no public product feed. **Google Shopping through Serper:** Serper's terms call its data "web-scraped" and Google is suing SerpApi (December 2025); showing those prices is a legal call for the owner. The research recommends using search results only to DISCOVER shop pages, and showing only prices read from the shop's own page.

**Checking a picture (R2).** Layered and cheap: (1) take the image from the same shop page as the accepted price; (2) simple guards: https only (the iPhone refuses plain http), a host allow list, size and shape, and the brand plus a line word in the image's title or source; (3) a fingerprint (perceptual hash, imagehash BSD-2) of each verified image, reused for free; (4) only then, a Claude Haiku yes/no look at the image, about USD 0.0002 per image, when the vision role is on. CLIP/SigLIP only as a fallback (heavy to host).

**Claude for extraction (official docs, re-checked by the reviewer).** claude-haiku-5-5: USD 0.10 / 0.50 per million tokens in/out (cache read 0.01); claude-sonnet-5-5: 2 / 10. Structured outputs with a strict JSON schema guarantee valid output (they cannot be combined with citations in one request). The server-side web search tool costs USD 10 per 1,000 searches, supports allowed/blocked domain lists (never both), and always cites; web fetch costs only tokens and honours robots.txt. Prompt caching from 512 tokens; the Batches API halves token prices (most batches within an hour). **Fit:** on the live path, Haiku over pages we already fetched, with a strict schema and low effort (about USD 0.001 per product), no live web search (each adds 1-3 s and USD 0.01). Offline, a catalog builder with Batches plus web search limited to vetted shop domains (about USD 0.01-0.03 per product with Haiku, 0.03-0.06 with Sonnet for hard names).
