## Two things about #94 that did not survive checking

1. **"They have been escalating to PAID render" is not reproducible.**
   `status="render-only"` is not in `source_router._ADMITTED_STATUSES` (only
   `"live"` is), so none of the four rows was ever in `SOURCE_REGISTRY`, and
   `is_render_only_domain()` returned `False` for all four with
   `ENABLE_BH_GCC_CATALOG_SOURCES=true`. They were inert, not expensive. The
   DATA was still wrong, and the label would have cost money the moment a
   liveness sweep promoted the row — which is exactly what a correct row now
   does, on the free path.

2. **`letoile.ae` is a Shopify storefront**, not the "Next.js, price plain-text
   client-side" the catalog claimed — `/products.json` is reachable and PDPs live
   at `/products/<handle>`. It is left as a plain curl row anyway: the
   consolidation demotes a non-bahrain-tier Shopify row to a plain discovery row
   regardless, and re-platforming a row is out of scope for #94.

Also recorded while probing: `matalanme.com` and `bfab.com` are the SAME
storefront (a matalanme PDP publishes its JSON-LD offer `url` as `bfab.com` and
its images from `admin.bfab.me`). And both publish `"price": 0` in JSON-LD for
configurable multi-size products — the `bolo.bh` class the extractor correctly
refuses. Sample URLs were chosen from simple products that carry a real price.

## The pipeline fix — why a generated-file edit would not have held

`data/bh_gcc_sources.json` is GENERATED by
`scripts/build_source_registry_data.py` from the four discovery catalogs, so the
correction was applied at the source: all four rows live in
`data/bh_gcc_source_candidates_round2.json` and each carried
`mechanism: "render_required"` +
`integration_adapter: "render tier Firecrawl/Scrape.do (is_render_only=True) - DEFER"`.
They now carry `mechanism: "curl_jsonld"` +
`integration_adapter: "fetch_page_price (mechanism=curl)"`, corrected
`sample_pdp_url`s, and a dated `measured` probe record (#94 item 5) that the
generator propagates onto the generated row.

Two generator bugs blocked that from working:

- **The idempotent merge preserved a stale `render-only` status.** It carried
  any prior status in `("live", "render-only", "dead")` forward, so a row whose
  catalog mechanism had just been corrected got its `render-only` status pinned
  straight back on the next rebuild. `_merge_prior_verdicts` now preserves
  `render-only` only while the row is still `is_render_only`; `live`/`dead` are
  verdicts ABOUT the source and are still never clobbered.
- **A rebuild silently DELETED five demotion tombstones.** Four non-retail
  demotions were followed by a generator skip (`_NON_RETAIL_DOMAINS`) and
  `footlocker.com.bh` became a registry literal, so a plain re-consolidation
  dropped all five rows — and with them the "Do not re-promote" rationale that
  is the entire point of a demotion. Pre-existing drift, surfaced by the first
  rebuild in this unit. `_merge_prior_verdicts` now keeps `status="dead"`
  tombstones the consolidation no longer emits (the loader never admits them, so
  they cost nothing), and does NOT resurrect a dropped `live` row.

## Verification

- **Rebuild diff:** `python -m scripts.build_source_registry_data` -> 368 rows
  before and after, identical row ORDER, **exactly four rows changed**
  (`bfab.com`, `letoile.ae`, `matalanme.com`, `xcite.com`), none added, none
  removed.
- **Liveness gate:** `scripts/verify_bh_gcc_sources.py` gained a `--domain`
  filter so a corrected row can be re-verdicted without re-writing all 368
  statuses in the same pass. Controls passed;
  `--domain matalanme.com,xcite.com,bfab.com,letoile.ae` ->
  `live=4 dead=0 inconclusive=0`, all four `http=200 +price`.
- **Flag-OFF byte-identity:** with `ENABLE_BH_GCC_CATALOG_SOURCES=false`,
  `SOURCE_REGISTRY` is 44 rows with an identical sha256 at base and at HEAD.
  With the flag ON it goes 315 -> 319: exactly the four rows added, none removed.
- **Tests:** `tests/test_registry_row_corrections_94.py` (30 nodes) pins both
  ends — the catalog rows AND the generated rows — plus the merge rules, so a
  future rebuild cannot regress them. The 41 test files that reference
  `source_router` / the generator / the data file were run at base and at HEAD:
  647 passed, and the single failure
  (`test_supplement_branch_genuine.py::TestCatalogSupplementSourceAttribution::test_cde2_attributes_catalog_supplement_domain_when_flag_on`)
  fails identically on the base commit — pre-existing, not a regression.
