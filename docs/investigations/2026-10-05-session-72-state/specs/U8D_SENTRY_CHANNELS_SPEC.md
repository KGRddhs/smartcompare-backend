## 3. Design

### 3.1 Per-site (the U8b/U8c pattern) versus one central policy

Per-site edits (type-only log + `from None` at each of the 5 in-route 500s, the middleware, 60 ERROR sites, 239 + 194 breadcrumb sites) are 400+ lines in 30 modules, regroup hundreds of Sentry issues, and still leave C5-C8, which no log line causes. The measured alternative is ONE policy inside `app/services/sentry_service.py` (plus two init arguments): it closes C1-C8 at the point where every event, transaction and breadcrumb already passes, keeps Railway logs byte-identical, and changes no response, status code or route.

### 3.2 The candidate policy that was measured (P1-P6) and the proposed rules (R1-R8)

Measured in memory (probe `policy` variant and `u8d_policy_plugin.py`):
- P1 every `exception.values[i].value` -> `""` unless `type == "HTTPException"` (type, module, mechanism, stacktrace kept);
- P2 the text of every exception "currently handled" (the chain, by `__cause__`/`__context__`, max 10, of `sys.exc_info()[1]`, of `hint["log_record"].exc_info[1]` and of `hint["exc_info"][1]`), as `str(x)` and `repr(x)` of length >= 4, replaced by `<TypeName>` in `logentry.message`/`formatted`/`params` and in breadcrumb messages (in `before_breadcrumb`, which also runs inside the except arm). Measured: `Cache delete error: <ConnectionError>`, `Share token creation failed: <ShareTokenError>`, `Unhandled RuntimeError: <RuntimeError>`, `push token update failed for user-u8d: <APIError>`, `Failed to log audit event 'login_failed': <ConnectError>`; the clean type-only lines (`Auth error in login: ConnectError`) unchanged;
- P3 `max_request_body_size="never"` (SDK option): no `request.data` on any event or transaction (measured on compare_post, login_body, unhandled_body);
- P4 every query-string value -> `[Filtered]` (keys kept) - this variant breaks 4 existing pins, see 3.3; R4 below is the pin-compatible form;
- P5 span `data["http.query"]` and http-breadcrumb `data["http.query"]` values -> `[Filtered]`, span `description` query stripped;
- P6 `request.url` path segment after `/api/v1/share/` and `/api/v1/referrals/invite/` -> `[token]`.

## 6. Data contract after the unit (what an event may contain)

- `exception.values[]`: `type`, `module`, `mechanism`, `stacktrace` (no `vars`); `value` = `""`, or the literal `detail` of an `HTTPException`.
- `logentry.message` / `formatted`: the log template with every handled exception text replaced by `<TypeName>`; `params`: strings with the same replacement.
- `breadcrumbs`: ERROR-level log lines only (R7 = ERROR), same replacement; http crumbs with `url` (scheme, host, path), method, status, and `http.query` values `[Filtered]`.
- `request`: method, scrubbed headers, `url` without query and with capability path segments `[token]`, `query_string` with PII parameters `[QUERY_REDACTED]` and credential shapes scrubbed; no `data`, no cookies.
- `extra`: `sys.argv`, the middleware's `request_id`/`method`/`path` (path tokens `[token]`); `tags`: `comparison_renderable` only; `user`: none; `contexts`: runtime/os/trace (trace ids restored as today).
- transactions: the same `request`; spans with `op`, `description` (no query), `data` with `http.query` values `[Filtered]`, model/token counts from the OpenAI integration (no prompts).

## 7. Edge cases (each needs a test or a stated limit)

1. A handled exception whose text is shorter than 4 chars (`KeyError('id')` -> `'id'` is 4) - below 4 nothing is replaced, so `x` in a template is never rewritten; pin with an exception text `"x"` and a template containing `x`.
2. Exception text that occurs inside the template's constant part (e.g. `RuntimeError("failed")` and the template `"... failed: %s"`) - both occurrences become `<RuntimeError>`; harmless, pinned so a GREEN cannot "fix" it by anchoring to the tail only without a ruling.
3. `__str__` raising / `__repr__` raising - skipped; the event still ships (pin).
4. Cyclic chains (`a.__context__ = b; b.__context__ = a`) - bounded walk (pin).
5. A log line emitted OUTSIDE the except arm about an earlier exception (fire-and-forget done-callbacks, `task.exception()`) - `sys.exc_info()` is empty; WARNING-level today, so R7 = ERROR removes it from Sentry; at ERROR it would leak (stated limit; the static ratchet in follow-up U8e).
6. ## 10. Flag policy

## 12. Assumptions (with the reason each beats the alternative)

- The privacy sentence is about Sentry only; Railway logs (#301's text in stdout) are out of this unit's scope - the sentence names Sentry, and changing Railway text costs triage for no Sentry gain once R7 lands.
- Blanking values (R1) beats scrubbing them (`exc_summary`-style): a scrubbed value still carries emails, row values and query fragments (C13: `exc_summary` removes only URLs and key shapes), so it cannot make "not raw exception text" true.
- Keeping chains (no new `from None` sites) beats de-chaining: with R1 the chain carries types and stacks only, which is the debugging value, and five route edits become unnecessary.
- A denylist extension (R4) beats an allowlist for inbound query strings because the R21 preservation contract is pinned by four existing tests (measured to fail under the allowlist-free P4); the ratchet test removes the denylist's drift risk.
