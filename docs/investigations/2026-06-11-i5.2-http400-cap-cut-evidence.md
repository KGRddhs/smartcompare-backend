# I5.2 — Evidence: the baseline's 39 http_400 rows are 30s cap-cuts

**Date:** 2026-06-11 · **Lane:** I5 "Yield & Wall" (Bundle B S2) · **Branch:** feature/s2-i5-yield-wall
**Baseline:** eval_runs `4aee8e88-da97-41b3-974b-3e75c2c9c10e` — 39 http_400 + 1 timeout (elec-019) all carry `wall_over_cap=true`; the 6 http_502 do NOT.
**Gate condition (dispatcher):** confirm http_400 = cap-cut BEFORE any Wave B lever work; if the mechanism is NOT the 30s outer `wait_for` surfacing as 400, STOP and report.

**Disposition: CONFIRMED.** The mechanism is the `STREAM_HARD_CAP_SECONDS` (30.0) outer `asyncio.wait_for` in `compare_from_text` surfacing through the route's failure-mapping as HTTP 400. Wave B levers are cleared to proceed.

## Evidence chain (dispatcher-ruled acceptable: (a) code-path proof + (b) recorded correlation)

### (a) Code-path proof — the only >30s-wall 400-producer is the cap handler

The eval runner calls `GET /api/v1/text/compare` (`scripts/eval_runner.py:500`) with `timeout = max_wall + 10s` slack (`:494`), and records `http_{status}` for any non-200 (`:505`) plus `wall_over_cap = wall_ms/1000 > cap` (`:574`). A client-side timeout would instead be recorded via the `httpx.TimeoutException` branch (`:506`) as a different error string — so the 39 `http_400` are genuine server 400 responses, not runner-side timeouts.

Tracing a >30s wall to the response:

1. `compare_from_text` (`app/services/structured_comparison_service.py:1191-1218`) wraps `_compare_from_text_impl` in `asyncio.wait_for(..., timeout=STREAM_HARD_CAP_SECONDS)`. On `asyncio.TimeoutError` it does NOT raise — it RETURNS `{success: False, error: "...", code: "TIMEOUT", total_cost: ...}` (HTTP-level still 200 at the service boundary). Pinned by `tests/test_compare_from_text_hard_cap.py`.
2. The GET handler `text_compare_get` (`app/api/text_routes.py:296-314`) sees `not result.get("success")` and — because `code != "CONTENT_UNAVAILABLE"` (the only early-return discriminator) — raises `HTTPException(status_code=400, detail=...)`. The POST handler shares the identical mapping (`:151-174`).
3. The eval runner records `http_400` + `wall_over_cap=true`.

**Why the cap handler is the ONLY 400-producer reachable after a >30s wall** (the dispatcher's stated sufficiency condition): every OTHER 400/4xx in `text_compare_get` fires BEFORE `compare_from_text` is called, so before any wall accrues:
- `422` dual-shape validation — "send EITHER q OR pair" / "send one of them" (`text_routes.py:236-245`), evaluated on the query params at entry.
- `429` usage-limit (`:271-279`), evaluated before the service call.
There is no post-service 4xx other than the `success:False → 400` at `:311`, and the only `success:False` path that takes >30s is the `code:TIMEOUT` cap-cut (the early-return content/INSUFFICIENT_DATA paths return well before 30s). Therefore a 400 with `wall_over_cap=true` is necessarily the cap handler.

This mapping is now pinned by `tests/test_http_400_cap_cut_mapping.py` (4 tests): GET+POST TIMEOUT→400, CONTENT_UNAVAILABLE→200 (discriminator guard), success→200 (anchor). So the mechanism can't silently change and invalidate the error-recovery arithmetic.

### (b) Recorded correlation — 39/39 http_400 (+ the 1 timeout) carry wall_over_cap=true

From the baseline per-query evidence (dossier §1/§4): all 39 http_400 + the 1 hard timeout carry `wall_over_cap=true`; the 6 http_502 do not. A 40/40 alignment of "400-or-timeout ⇔ over-cap" with zero over-cap 200s among them is exactly what the code path predicts (over-cap → TIMEOUT → 400), and the 502s being uncorrelated matches them being upstream transients on a different path.

## Scope of the claim (honest bound)

This confirms the MECHANISM that converts a >30s wall into an http_400 — it does NOT assert anything about WHY individual queries breach 30s (that's the per-query latency work in Wave B levers I5.6/I5.7 + the registry/discovery fixes I5.3-I5.5). The recovery arithmetic in the dossier (46 error rows → graded-rate recovery) rests only on "these rows zero all axes because they 400'd, and the 400 is a wall artifact, not a genuine data failure" — which is what this establishes.
