## 0 What the unit does

The Results screen asks the one question the learning loop needs: did we compare the right products. Today `SmartCompareApp/src/components/FeedbackCard.tsx` (132 lines) shows "Was this helpful?" with three positive-only chips (Accurate / Detailed / Fast) and posts `{useful: true, comparison_id, mattered_most}` through `submitFeedback` (`src/services/api.ts:1065`). No client code sends an identity or correctness answer, so the D22 buckets read 0 and the judge has no user "No" to escalate on. CL3 replaces that card. Two one-line riders travel with it: S81-24e (ForgotPassword maps the coded RATE_LIMITED) and the ContactUs source line.

The wire contract already on main, dark behind ENABLE_FEEDBACK_V2 (`app/api/feedback_routes.py:226-245`): `useful: Optional[bool]`, `identity_correct: "correct" | "wrong" | "unsure"`, `wrong_side: "first" | "second" | "both"`, `preference: "first" | "second" | "neither" | "unsure"`, `correction: str` (refused past 80 raw characters and on control characters, :155 / :261-274), `source: "result" | "contact"` (default "result"), `compare_request_id` (a UUID, :163-174). With the flag OFF the frozen base model applies (`useful: bool` required, :201).

## 1 Rulings (binding on the spec; the spec refines names and mechanics, never widens scope)

- R-CL3-1 SCOPE: (a) the feedback card; (b) S81-24e; (c) the ContactUs source line; (d) the i18n keys, the tests and the CLAUDE.md entry they need. OUT: CL4, S81-11c / S81-11d, the image_load_failed emission, any backend file, any native or app.json change, any new event type (the events fence), any new dependency, any remote flag.
- R-CL3-2 Q1, ALWAYS, ONE TAP: "Did we compare the right products?" with three answers Yes / No / Not sure = `identity_correct` correct / wrong / unsure. Yes and Not sure: ONE POST, then the thanks state.
- R-CL3-3 NO IS RECORDED AT THE TAP: tapping No posts `{identity_correct: "wrong"}` at once (the most valuable answer is never lost to an abandoned follow-up), then the card shows the OPTIONAL details step: "Which one did we get wrong?" with three choices labelled by the two product names in the result's own order (first / second) plus "Both", one single-line text field (maxLength 80, optional: the right product's name) and Send / Skip. Send posts ONE more row `{identity_correct: "wrong", wrong_side?, correction?}`; it is enabled once a side is chosen or the trimmed text is non-empty. Skip, or leaving the screen, posts nothing more. So a card writes one row, or two when the user volunteers details; both carry the same ids. The spec MEASURES how `scripts/cron_learning.py` and `scripts/cron_compare_judge.py` read several feedback rows for one comparison and states it; a reader that double-counts is a recorded follow-up for D22b (a reader-side dedupe), never a reason to delay the No.
- R-CL3-4 WIRE: the card sends only `identity_correct`, `wrong_side`, `correction`, `preference` (R-CL3-8) and the ids; it NEVER sends `useful` or `mattered_most`, and it leaves `source` to its default. `submitFeedback`'s parameter type is widened additively (`useful` becomes optional). Every POST stays fire-and-forget with the existing double-tap guard: a failure never shows an error and never blocks the thanks state.
- R-CL3-5 IDS: `comparison_id` when the result has one (as today, `ResultsScreen.tsx:459`); `compare_request_id` = the id the compare's own requests carried (S81-08, R-S08-15: `IdentifyResultWithRequestId`, `newCompareRequestId` / `withRequestContext`), when the Results screen can know it. The spec measures the carrier for each entry (text REST and SSE, camera, URL) and proposes the smallest additive plumbing; where no id reached the screen the field is omitted. An id is never minted for the feedback call.
- R-CL3-6 WHEN IT APPEARS: the card is not rendered until the first of (a) 8 seconds of dwell on a rendered, delivered comparison, (b) the verdict section scrolled into view. NEVER on a History reopen (`openedFromHistory`, `ResultsScreen.tsx:645`: a `comparison_id` route param). Once revealed it stays; once answered it shows thanks and does not ask again for that result. It mounts where the old card mounts (the spec cites the line), so the reveal moves nothing above it. No new dependency: the existing scroll container's layout and scroll events. Reduce-motion users get no animation. A result that is a refusal, an abstain, a timeout or a partial has no card (the spec states the existing mount condition and keeps it).
- R-CL3-7 THE CORRECTION TEXT IS PRIVATE: it travels only in the feedback POST body. Never in an analytics event, a console or Sentry line, a breadcrumb, or storage. Single line; trimmed; control characters and newlines removed client-side before the send (the backend refuses them with a 422, and the card is fire-and-forget).
- R-CL3-8 Q2 EXISTS BUT IS OFF: "Which one would you pick?" = `preference` first / second / neither / unsure, asked only after Q1 = correct, ONE more row. It sits behind a compile-time constant in `src/config/features.ts` (the spec names it; value false), NOT a remote flag: with the constant false nothing of Q2 renders and `preference` is never sent (a RED row pins it). Turning it on is a later OTA after Q1's answer rate is read. The spec checks RULINGS_S81_SF1 and the SF1 brief for the meaning of `preference`; a mismatch with this reading is a question, not a guess.
- R-CL3-9 REMOVED: the title "Was this helpful?", the three chips, `useful: true`, `mattered_most` from the card; the keys `results.feedback.title` / `.accurate` / `.detailed` / `.fast` / `.placeholder` / `.submit` leave en.json and ar.json when the spec proves no other reader (key-set equality holds); `results.feedback.thanks` is kept or reworded.
