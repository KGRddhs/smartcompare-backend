## Blocking rulings
- R-S08-1 (BL1; RF1; C1): the compare id is minted at the CALL SITES, never from a path list: `streamComparison` mints one id and sends it on the SSE request and the REST fallback (exposed as `compareRequestId`); `identifyFromImages` mints one id for both camera attempts and exposes it additively; Link mode passes `headers: {'X-Compare-Request-Id': ...}` in its existing HomeScreen request config (kept by only-if-absent). `COMPARE_REQUEST_PATHS` is dropped, so `consent/aiDispatchFence.s69` stays unedited and green; M11 / B3 fall away.
- R-S08-2 (BL2; RF9; C9; spec Q7; CROSS-UNIT with S81-09): the reset time renders only on the DAILY axis. The sheet's daily state renders it always; the sheet's open / unknown states and the Home pill render it ONLY when the status names the counted axis: S81-09's `/usage/status` carries `counted_scope` and its USAGE_LIMIT detail carries `scope`, both in {'daily', 'device_daily', 'monthly', 'lifetime'} (the contract is fixed HERE for S81-09), and the client renders the line only for 'daily' / 'device_daily'. The a11y copy never says the bonus refreshes. Until S81-09 ships, the pill and the open state render nothing new (today's tree byte for byte).
- R-S08-3 (BL3; RF8; C6, C7; contract risk K2; spec Q5, Q6): NO device-level consent mirror in this unit. Consent stays PER ACCOUNT: every account sees the sheet once per version (guideline 5.1.2(i): the permission is the person's, and a second account on one device may be another person), the X-AI-Consent-Version header is read from the ACCOUNT record only, a signed-out user keeps today's behaviour (asked every time, nothing persisted, no header), and a `getSavedUser` THROW omits the header (B15). No device id, derived tag or fallback-derived value is ever written to AsyncStorage (A9b). The consent read on the request path uses an in-memory memo invalidated by recordAiConsent / clearAiConsent / sign-out. PLAN_S81's "consent re-keyed to device as well as account" is SUPERSEDED by this ruling; RULINGS_S81_12 R-S12-10 is amended: privacy s14 keeps "deleting your account removes the AI permission record" and drops the device-level-copy sentence (the device-identifier sentence stays).
- R-S08-4 (BL4; RF11; C8; K1, K7; spec Q1, Q2): the legacy fingerprint rides ONLY where a stored row is matched: `/api/v1/auth/register`, both social sign-ins and the share path (the body today; the header `X-Device-Fingerprint-Legacy` beside it) plus the invite / quiz routes if the backend matches there; never on compares, usage status or any other request (the osBuildId composition stays at three call sites, not on every request). A NEW small additive backend unit **S81-08b LEGACY-FINGERPRINT-READER** (unflagged-safe: build 3 never sends the header; a stored-row match at register, social sign-in and the SAME_DEVICE checks accepts the new value OR the legacy value when the legacy header is present and valid) must be LIVE before the first OTA: DEFECT_LEDGER records it as the OTA precondition. The runtime cutoff constant 2027-03-31T21:00:00Z (self-ending) is accepted; every legacy-dependent row pins Date.now to a fixed pre-cutoff instant and one row runs at a post-cutoff instant (no legacy header; C5).
