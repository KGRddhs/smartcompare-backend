## Design rulings
- R-ST1-1 (B3, Q1): the binding PLAN_S81 M1 text wins over the brief: the Supabase half goes through the EXISTING `run_db` helper and therefore honours ENABLE_SYNC_DB_OFFLOAD exactly like every other hot-set site. `run_db_offloop` is DROPPED (no new DB dispatch helper). Under ST1 ON with ENABLE_SYNC_DB_OFFLOAD OFF (production today) the Supabase reads stay inline and only the two Upstash GETs move to the redis-offloop pool; with both ON everything leaves the loop. One DB-offload switch; the flip order pairs the two flags in one window ("ENABLE_SYNC_DB_OFFLOAD + ST1").
- R-ST1-2 (B2, contract risk 2, M17, L7): NO blocking twins. The base `_get_user_tier_info` and `_get_active_referral_bonus` are async and already call run_db (M13-05); the ON path gathers THEM, byte-unchanged, with the two pool GETs: `await asyncio.gather(_get_user_tier_info(user_id), _get_active_referral_bonus(user_id), run_redis_offloop_pool(_get_redis_count, daily_key), run_redis_offloop_pool(_get_redis_count, monthly_key))`, the two date keys computed on the loop before the gather (as specified). Consequences: B2 (unpinned twin query chains) is moot because no query chain is copied (the RED still records the chains of the existing helpers once, as PIN rows, so a later edit of either helper is seen); the duplication risk is gone; the twin log templates and L7 vanish; the base helpers' own except arms keep their base text and fallbacks (the `[USAGE-OFFLOOP] tier info / referral bonus read failed` templates are deleted). The ON fork's except covers only a pool dispatch failure (RuntimeError) and falls back to the base inline body (R14 rows, correction 4).
- R-ST1-3 (Q4): ONE compute body. `_usage_status_body(user_info, bonus, daily_used, monthly_used)` and `_usage_allowed_body(...)` are extracted as pure functions and the base (OFF) tail CALLS them too (a pure extraction refactor), so S81-09 edits one body. Flag-OFF identity is pinned by behaviour, not by code shape: the base-recorded response literals in base key order (correction 1: free_paid_window as recorded, premium_bonus and the lifetime-free case recorded the same way), the op sequence and thread placement against the 1.6 base literals (R12 / R13, correction 3), and the W4-13 flag-off ledger. The OFF-tail AST digest (R25, correction 2) is dropped as inapplicable; the consume / refund / key-helper digests of 2.7 stay.
- R-ST1-4 (B1, Q2, MAJ-1): option (b). The post-extraction reviews L1 write (and each re-cache write at the :753-754 / :767-768 sites) becomes a DURABLE, NON-AWAITED pool write on a deepcopy snapshot of the reviews dict, so the response is never delayed and the 10 s Phase-1 reviews cap can no longer drop the reviews because of a queued write (probe D). Ordering per cache_key within a request: a later write for the same key awaits the previous write's handle before submitting (a per-request chain), so the last snapshot wins as at base; the L2 save is scheduled before the write as the spec says; the L2-promotion write stays inline (spec L1, the S77 RO17 reorder class). RED rows: the probe-D scenario (pool of 4 saturated by 1.0 s jobs, a 0.5 s cap) returns the extracted reviews under ON and the write lands after the response; two writes for one key land in order; a reviews-race cancel still lands the write (shield); the stored value equals the snapshot taken at write time even when the caller mutates the returned dict afterwards. Mutants: the write awaited (reddens the saturation row), no chain (the order row), no deepcopy (the snapshot row), not shielded (the cancel row). Section 9 and the canary name the remaining pool-load effect (L3).
