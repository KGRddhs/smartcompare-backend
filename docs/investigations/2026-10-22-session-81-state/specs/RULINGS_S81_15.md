## Design rulings
- R-S15-6 (refuted R-4, R-5; correction C5): the QarenBot UA constant moves into the leaf `app/services/robots_eval.py` (`QARENBOT_UA`) and `sitemap_discovery_service._ROBOTS_UA` becomes a re-export of it (byte-identical value); `robots_registry` imports it from `robots_eval`, so importing the cron module never loads price_service or extraction_service (R37 holds). - R-S15-7 (refuted R-9, R-11, R-12; corrections C1, C2, C3): memo design. The refresh is dispatched with `asyncio.to_thread` UNCONDITIONALLY when a running loop exists (no `ENABLE_SYNC_DB_OFFLOAD` precondition; `run_db` is not used for this read), bounded by `asyncio.wait_for` under `MERCHANT_REGISTRY_READ_TIMEOUT_SECONDS` (default 5.0, clamp 1..30, defensive parse, read per refresh); a timeout or any exception is caught inside the task; with no running loop (sync callers, import time, most tests) the accessor returns the fallback and schedules nothing. The snapshot is a sha256 over the decode-relevant columns of the fetched rows (host, status, deny, blocked_reason, registry, partner) PLUS the `ENABLE_BH_GCC_CATALOG_SOURCES` state, never `max(updated_at)` (one NULL freezes a string max; an owner SQL edit without a bump is invisible). After a good DB load, a FAILED refresh keeps the last good DB list for up to `MERCHANT_REGISTRY_MAX_STALE_SECONDS` (default 3600, clamp 900..21600); past that it falls back to `SOURCE_REGISTRY` with one WARNING by type per window (reverting at once would re-admit every robots-blocked host for a whole window). The list object identity is kept across equal snapshots (the D03 `_ROUTABLE_MEMO` identity holds). Mutation table: P1 and P2 do not kill M1 (no running loop); the kill rows run inside a loop (P3 and new P-rows); the table is re-derived.
