## 2. Blocking issues

B1 (R-1, R-2): the decode must not make a blocked or denied row disappear from the LOOKUP consumers while there is no fetch chokepoint for it. Two acceptable shapes for a ruling: (a) split the accessor: the selection consumers (`get_*_sources_for_category`, `_direct_fetch_sources` and its seven selectors, `get_gcc_shopify_pagescrape_sources_for_category`, `build_site_discovery_query`) iterate live rows only, while the lookup consumers (`registry_tier`, `match_registry_apex`, `_registry_row_for_host`, `score_source`, `source_usage`, `is_render_only_domain`, and the three direct readers) still see cron-blocked rows (for instance decoded with `Source.status = "blocked"`, a value no code-registry Source carries today: measured statuses `live` 279, `''` 39, `provider-test-candidate` 1), so `registry_tier("sephora.com")` stays `"global"`; or (b) couple the flag: the DB registry is effective only while `ENABLE_DATA_GUARDS_V2` is ON AND a blocked-host chokepoint exists (that is D14's surface, so (b) means this flag cannot flip before D14). Either way add pins: under the DB flag with a blocked global row, `_shopping_bh_host_evidence` keeps `global_tier`, `_organic_host_bh_gcc_retail` stays (False, False), `_is_genuine_bh_candidate` stays False; with D03 OFF the denied fragrantica row keeps its base answers. Rewrite the 0 / 8.1 "only live effect" sentence.

B2 (R-10): the cron's fetcher must follow redirects itself (RFC 9309 2.3.1.2: at least five hops), validating EVERY hop with `validate_external_url_async` (the `shopify_pdp_service._hop_is_allowed_async` / B4 `_fetch_page_v2` precedent), with `allow_redirects=False` on each curl call, a five-hop cap (beyond it = unreadable), and the final status deciding. R27's 3xx row becomes "a redirect chain that ends 2xx is readable; a chain past the cap or onto a refused host is unreadable". The same fetcher serves the promotion PDP fetch. Without it a merchant robots redirect reaches private / link-local / `*.railway.internal` addresses from the cron service.

B3 (R-7): extend the `robots` record additively so D14, D09 FEED-WALKER and S81-16 can answer per URL with no fetch: e.g. `rules = {"qarenbot": [[allow, pattern], ...], "star": [...]}` (the merged rule lists `robots_eval._rules_for_agent` would use for each agent, capped at `MAX_RULES` / a byte cap), plus `origin` (the scheme+host the file was read from). Keep `state` but define it as the verdict on a stated probe set (the sample PDP path AND "/" AND the adapter endpoint path for the row's mechanism), most restrictive wins. Pin the shape as the D14 contract (a test that evaluates a URL from the stored record equals `can_fetch` on the original body for both agents).

B4 (R-6): add the Option C path: an owner / operator-recorded residential read (`robots.source = "residential"`, its own `fetched_at`, the rules of B3) that the datacenter cron never downgrades to `unreadable`; the cron may record its own datacenter outcome in a separate key (`robots.dc_status`). Seed or document the three named hosts as the first Option C rows (owner step, names only). Rewrite L9.

B5 (R-3, R-13): list E1 = `tests/test_legal_disclosure_s77.py::test_s77_d9_bot_page_claim_matches_the_runtime` (widen `QARENBOT_FILES` by the new emitters, keep `can_fetch` in each) and decide whether the `/bot` page text (EN + AR, `landing/bot/index.html`, pinned at `:181-187`) still describes the cron truthfully ("Our site-discovery crawler (QarenBot) reads and follows robots.txt") or must change; a change is a public-page + Arabic copy edit ([NATIVE READ]) and a landing redeploy (the third lever), most likely owned by S81-12 LEGAL-V3. Add the file to the change list or record the dependency.
