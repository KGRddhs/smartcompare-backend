# AI Guidance System Design

**Date**: 2026-03-11
**Approach**: Scoring-First Guidance (Hybrid)
**Cost Impact**: ~$0.000015 extra per comparison (~20 input tokens for schema + ~50 output tokens for insights)

## Overview

Enhance the ResultsScreen with smart, personalized guidance that helps users understand which product is best for THEM. Three components:

1. **Winner Badges** (deterministic from scoring data, $0)
2. **Personalized Insight Cards** (GPT-generated, rides on existing verdict call)
3. **Improved Fallbacks** (smarter backend data sourcing + graceful UI degradation)

Anonymous users see a prompt to set preferences instead of personalized content.

## Part 1: Winner Badges

### What
Per-aspect winner badges derived from the existing `scoring.scores.product_N.breakdown` data. Each product earns badges for dimensions where it scores higher.

### Badge Mapping

| Scoring Dimension | Badge Label | Condition |
|---|---|---|
| `price_score` | Best Price | Winner by >= 3 points |
| `spec_score` | Best Specs | Winner by >= 3 points |
| `review_score` | Top Rated | Winner by >= 3 points |
| `value_score` | Best Value | Winner by >= 3 points |
| `reliability_score` | Most Reliable | Winner by >= 3 points |
| `popularity_score` | Most Popular | Winner by >= 3 points |
| Overall winner | Best for You (personalized) / Best Overall (anonymous) | Overall score winner |

**Threshold rationale**: 3 points on a 0-100 scale filters noise from normalized scores. Represents ~5% meaningful difference — below this, products are too close to distinguish on that dimension.

### Logic
- Pure frontend code — no backend changes needed
- Compare `product_0.breakdown[dim]` vs `product_1.breakdown[dim]`
- Winner of each dimension gets the badge; if difference < 3 points, no badge (too close to call)
- Maximum 6 aspect badges + 1 overall badge per product
- Use `result.personalized === true` to determine overall badge label ("Best for You" vs "Best Overall")
- If `result.scoring` is null/undefined, render no badges at all

### UI Placement
- Horizontal row of small colored chips below product name in ProductCard
- Replaces the binary "WINNER" badge with richer per-aspect information
- Colors: green chips for the overall winner, blue chips for aspect wins on the non-winner

### Files Changed
- `SmartCompareApp/src/screens/ResultsScreen.tsx` — new `AspectBadges` component, updated `ProductCard`
- `SmartCompareApp/src/types.ts` — badge type definitions (if needed)

## Part 2: Personalized Insight Cards

### What
2-3 insight cards after both ProductCards but before the ScoringSection in the Overview tab. They explain WHY specific aspects matter to this user. Generated by GPT in the existing verdict call.

### Examples
- "Since you prioritize battery life, Product A's 5000mAh vs 3349mAh means ~2 hours more screen-on time"
- "You prefer budget options — Product B is 15% cheaper at $799 vs $949 while matching camera quality"
- "As a fitness enthusiast, Product A's IP68 water resistance is worth the $50 premium over Product B's IP54"

### Backend Changes
Add `personalized_insights` field to the COMPARISON_PROMPT JSON output schema:

```json
{
  "personalized_insights": [
    {
      "focus_area": "string (required, e.g., 'battery_life', 'price', 'camera', 'durability')",
      "product_index": "int, 0 or 1 (required, which product this insight favors)",
      "insight": "string (required, max 200 chars, 1-2 sentences with specific numbers)"
    }
  ]
}
```

**Schema rules:**
- `focus_area`: free-form topic name (NOT the same as scoring dimension names). Maps to user priority or lifestyle tag.
- `product_index`: required, 0 or 1. Which product this insight favors.
- `insight`: required, max 200 characters. Must include a specific number/fact.
- Array: 2-3 items, each tied to a user priority from their preferences.

**Prompt instructions to GPT:**
- Only generate `personalized_insights` when user preferences section is present in the prompt
- Generate exactly 2-3 insights, each referencing a different user priority
- Each insight must cite a specific spec/price/rating number

**Backend validation (in `generate_comparison()`):**
- If `user_preferences` is null/empty: strip `personalized_insights` from response entirely
- If GPT returns >3 insights: truncate to first 3
- If GPT returns 0 insights despite preferences: set `personalized_insights: []`
- Frontend handles `personalized_insights: []` by showing PreferencePromptBanner fallback

**SSE streaming**: Include `personalized_insights` in the `verdict` SSE event payload (same event that contains winner_reason, pros, cons). No separate event needed.

### Frontend Changes
- New `InsightCard` component — styled card with focus area icon, product highlight, and insight text
- Rendered after both ProductCards, before ScoringSection in Overview tab
- Only shown when `result.personalized === true` AND `personalized_insights.length > 0`
- **Icons**: Use Ionicons mapped by focus_area keyword: `battery` → battery-charging, `price`/`budget` → cash-outline, `camera` → camera-outline, `durability` → shield-checkmark, etc. Default: `information-circle-outline` for unrecognized focus areas.

### Anonymous User Behavior
- No insight cards shown
- Instead, show a single `PreferencePromptBanner`: "Set your preferences for personalized guidance" linking to PreferencesScreen (if logged in) or LoginScreen (if anonymous)
- Also shown when `personalized === false` or `personalized_insights` is empty/missing

### Files Changed
- `app/services/extraction_service.py` — add `personalized_insights` to COMPARISON_PROMPT schema + instructions
- `SmartCompareApp/src/screens/ResultsScreen.tsx` — new `InsightCard` component, `PreferencePromptBanner`

## Part 3: Improved Fallbacks

### Backend: Smarter Data Sourcing

**Price fallback chain improvement (scope: 1 extra Serper call max):**
- When Serper Shopping returns 0 results AND organic search fails, try a broader search query before Tier 3
- Broader query: strip trailing model numbers/variants using regex `r'\s+(pro|plus|max|ultra|\d{2,}gb|\d+tb)$'` (case-insensitive)
- If broader search also fails: proceed to Tier 3 GPT estimate as today
- Max 1 additional Serper call per product (~$0.001 worst-case, only on current failures)

**Frontend: Graceful Degradation (all sections):**
1. **Empty section handling**: Hide spec rows with null/empty values instead of showing blank rows
2. **Missing price**: Show "Price not available" styled text instead of empty space; hide retailer line
3. **Missing rating**: Show "No ratings yet" instead of empty RatingDisplay
4. **Missing reviews**: Show "Reviews not available for this product" instead of empty ReviewsTab
5. **No scoring data**: Hide ScoringSection entirely; hide AspectBadges when `result.scoring` is null

**Deferred to future** (out of scope for this session):
- Snippet rating extraction from organic results (non-trivial regex, edge-case heavy)
- Site-specific spec gap filling (gsmarena.com, amazon.com) — adds complexity + cost

### Files Changed
- `app/services/structured_comparison_service.py` — broader fallback search in `_get_product_price()`
- `SmartCompareApp/src/screens/ResultsScreen.tsx` — null checks and graceful empty states for all sections

## Data Flow

```
Existing:
  Serper → GPT extract → Scoring Engine → GPT verdict → Response

New (additions marked with *):
  Serper → GPT extract → Scoring Engine → GPT verdict (+ *personalized_insights) → Response
                              ↓
                    *Winner badges (frontend, from scoring.breakdown)
                    *Insight cards (frontend, from verdict.personalized_insights)
                    *Preference prompt (frontend, when !personalized)
                    *Graceful empty states (frontend, null checks)
```

## Cost Analysis

| Component | Extra Cost | Reason |
|---|---|---|
| Winner badges | $0 | Pure frontend logic from existing scoring data |
| Insight cards | ~$0.000015 | ~20 input tokens (schema def) + ~50 output tokens (2-3 insights) |
| Fallback backend | ~$0-0.001 | 1 extra Serper call only when Tier 1+2 both fail |
| Fallback frontend | $0 | Pure UI logic |
| **Total** | **~$0.000-0.001** | Well within $0.015 budget |

## Testing Requirements (80%+ coverage)

### Unit Tests (Backend)
- `test_guidance_insights.py`: Verify `personalized_insights` field in verdict response, verify it's absent when no preferences, verify 2-3 insights generated, verify >3 truncated to 3, verify empty array when 0 insights
- Extend `test_streaming.py`: Verify insights included in `verdict` SSE event payload
- `test_fallback_improvements.py`: Broader search triggers only when Tier 1+2 fail, regex model stripping, max 1 extra call

### Unit Tests (Frontend)
- `AspectBadges` renders correct badges from scoring data
- Badge threshold: verify no badge when diff < 3, badge appears when diff >= 3
- Null scoring: verify badges hidden when `result.scoring` is null
- `InsightCard` renders insight text and focus area icon, correct icon mapping
- `PreferencePromptBanner` shown for anonymous users and when `personalized === false`
- Graceful empty states for all missing data scenarios (price, rating, reviews, specs, scoring)

### Integration
- Full comparison with preferences → badges + insights present
- Full comparison without preferences → badges + prompt banner, no insights
- Comparison with missing data → graceful degradation, no crashes

## Non-Goals
- No user-facing confidence indicators (covered by T&C)
- No conversational/chat guidance (sticking with smart highlights)
- No multi-product (3+) support (separate feature)
- No feature flags — if issues arise, remove `personalized_insights` from COMPARISON_PROMPT and redeploy

## Team Execution Strategy

### Token Limit Management (Pro Subscription)
- **2 agents per phase** (not 4) — Session 20 proved this works within Pro limits
- **Checkpoint files** after each phase — agents read checkpoint, not full conversation history
- **Context files updated** after each major step — MEMORY.md, session log
- **Agent prompts minimal** — task-specific context only, not full project history
- **Phase boundaries** — natural pause points where limits can reset
- Agents idle between phases can write red-green tests

### Cross-QA Protocol
- Each agent QAs the other's work before phase completion
- QA failures sent back to original agent with specific feedback
- No phase completes until both agents sign off
- Idle agents write tests targeting 80% coverage
