### 3.3 What a tap does today

No listener exists, and React Navigation's default `getInitialURL`/`subscribe` read only `Linking` (`useLinking.native.js:13-35`) — a notification response is not a `Linking` URL. So on every platform and every app state a tap on any Qaren push **opens the app wherever it last was** and `data.url` is never read. For the one live push this means: the referrer taps "X joined, +5 comparisons" and lands on Home (or the splash), not on their referral status.

### 3.4 Foreground pushes are dropped (no `setNotificationHandler`)

Installed native sources: Android `SingleNotificationHandlerTask.java:32` `SECONDS_TO_TIMEOUT = 3`; `start()` (`:67-74`) emits `onHandleNotification` to JS and arms the timeout; only `processNotificationWithBehavior` (`:88-108`) calls `NotificationsService.present(...)`; `handleTimeout()` (`:116-123`) emits the timeout event and `finish()`es **without presenting**. iOS `SingleNotificationHandlerTask.swift:34` arms a 3 s timer (`Timer.scheduledTimer(timeInterval: 3, … selector: #selector(timeout)`); `timeout()` (`:38-41`) calls `delegate.handleNotificationTimeout` then `finish()`, and `finish()` (`:53-57`) does `timer?.invalidate(); self.completionHandler = nil` **without ever invoking the `UNNotificationPresentationOptions` completion** — only `processNotificationWithOptions` (`:43-51`, reached from JS `handleNotificationAsync`) calls `completionHandler(options)`, so the OS presents nothing on timeout. `NotificationsHandler.js` only subscribes to `onHandleNotification` inside `setNotificationHandler(handler)`; with no handler set nothing answers, so both platforms time out. A Loop-2 push that arrives while the referrer is inside the app is therefore invisible.

### 4.2 `SmartCompareApp/src/services/pushNavigation.ts` — NEW (the listeners)

Lazy-require `expo-notifications` exactly as `pushTokenService.ts:50-56` does (a missing native module must never break boot), and expose four pure-ish functions:

```ts
// 1. URL → path. @react-navigation/native's "exports" map exposes only "." and
//    "./package.json" (package.json), so extractPathFromURL is NOT importable;
//    strip a matching prefix ourselves. Returns undefined for foreign URLs.
export function pathFromPushUrl(url: unknown, prefixes = linking.prefixes): string | undefined

// 2. path → { state, action } through the SAME functions useLinking.native.js:85-92
//    and :127-146 use: linking.getStateFromPath(path, linking.config) then
//    getActionFromState(state, linking.config). undefined when no route matches.
export function actionFromPushUrl(url: unknown): { state; action } | undefined

// 3. One response → one navigation. Guards: response non-null;
//    actionIdentifier === DEFAULT_ACTION_IDENTIFIER (a plain tap; Notifications.types.d.ts:589);
//    typeof data.url === 'string'; a resolvable route. If navigationRef.isReady()
//    → dispatch(action) (or resetRoot(state) when getActionFromState yields
//    undefined, mirroring useLinking.native.js:138-145); else park it in a
//    module-scoped `pending` slot drained by onNavigationReady(). Never throws.
export function handlePushResponse(response: NotificationResponse | null | undefined): boolean

// 4. Boot wiring. Idempotent. Sets the foreground handler
//    { shouldShowBanner: true, shouldShowList: true, shouldPlaySound: false, shouldSetBadge: false }
//    (NO deprecated shouldShowAlert — NotificationsHandler.js warns on it), registers
//    addNotificationResponseReceivedListener(handlePushResponse). Returns an
//    unsubscribe; returns a no-op when the module cannot be required.
export function installPushTapListeners(): () => void

// 5. Cold start. Reads getLastNotificationResponse() (sync on 0.32.17) inside
//    try/catch — the JS throws UnavailabilityError when the native module lacks
//    the function (NotificationsEmitter.js getLastNotificationResponse) — hands it
//    to handlePushResponse, then clearLastNotificationResponse() so a later
//    container remount cannot replay it. Called from NavigationContainer.onReady.
export function onNavigationReady(): void   // drains `pending`, then replays the cold-start response
```

**Why dispatch-after-ready instead of overriding `linking.getInitialURL`/`subscribe`** (the Expo docs pattern): a cold-start URL fed through `getInitialURL` becomes the container's *initial state*, and for a root-level route that state is a **single-entry root stack** — `{"routes":[{"name":"Results",…}]}` with no `Main` under it (§4.5 probe 3, "plain"), so the Results back arrow (`ResultsScreen.tsx:695` `navigation.goBack()`) is unhandled: the verifier's MB-FLOWS-STATE-04 class. The alternative `initialRouteName: 'Main'` in the path config fixes Results but ALSO prepends `Main` under `c/`, `q/` and `r/` (probe 3 "withInitial"), changing the live referral deep-link shapes — out of scope. Dispatching `NAVIGATE Results` over the already-initialised `Main` (probe 3 "actions") pushes the modal on top of Home, back works, and the warm-tap and cold-start paths share one code path. `useLinking.native.js:127-146` does exactly this for warm `Linking` URLs.

**Why a new module and not `pushTokenService.ts`** (the plan's file list): `tryRegisterPushToken` runs only after auth (`App.tsx:231,298`) and is permission-prompting; the tap listener and foreground handler must be armed at boot regardless of auth and must never prompt. Keep `pushTokenService.ts` byte-identical (its neighbourhood is inside the 25-suite gate set, §7.3).
